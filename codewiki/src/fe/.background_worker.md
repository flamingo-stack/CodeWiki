# background_worker.py

Implements a threaded background worker that processes documentation generation jobs asynchronously, handling repository cloning, documentation generation, caching, and job status persistence for the web application.

## Key Components

- **`BackgroundWorker`** — Main worker class managing a job queue and processing lifecycle:
  - `start()` / `stop()` — Launch/halt the daemon worker thread.
  - `add_job(job_id, job)` — Enqueue a new `JobStatus` for processing.
  - `get_job_status(job_id)` / `get_all_jobs()` — Query job state.
  - `load_job_statuses()` / `save_job_statuses()` — Persist job history to `jobs.json` on disk.
  - `_reconstruct_jobs_from_cache()` — Rebuilds job records from `CacheManager` cache entries for backward compatibility when the jobs file is missing.
  - `_worker_loop()` — Polls the internal `Queue` and dispatches jobs for processing.
  - `_process_job(job_id)` — Core job pipeline: checks cache, clones the GitHub repo via `GitHubRepoProcessor`, runs `DocumentationGenerator` in a dedicated asyncio event loop, updates cache/job status, and cleans up the temporary repo directory.

## Usage Example

```python
from codewiki.src.be.background_worker import BackgroundWorker
from codewiki.src.be.cache_manager import CacheManager
from codewiki.src.be.models import JobStatus
from datetime import datetime

cache_manager = CacheManager()
worker = BackgroundWorker(cache_manager)
worker.start()

job_id = "flamingo-stack--CodeWiki"
job = JobStatus(
    job_id=job_id,
    repo_url="https://github.com/flamingo-stack/CodeWiki",
    status="pending",
    created_at=datetime.now()
)
worker.add_job(job_id, job)

# Poll for status
status = worker.get_job_status(job_id)
print(status.status, status.progress)
```

## Notes

- Jobs are processed sequentially by a single background thread; the queue size is bounded by `WebAppConfig.QUEUE_SIZE`.
- Completed jobs are cached via `CacheManager` to avoid redundant regeneration for the same repository URL.
- Only jobs with `status == 'completed'` are reloaded from disk on startup to prevent inconsistent in-progress state.
- Temporary cloned repositories are removed via `rm -rf` in a `finally` block regardless of success or failure.
